# Q2.1 pressure panel driver

`research_loop.modular.pressure_panel_driver` is a train-only production seam.
The caller supplies one `q21-pressure-material-bundle-v1` record for every
prepared public task.  It binds the task identity and payload digest, then
contains exactly four real material rows: `support`, `refute`, `invalid`, and
`unknown`.  Those identifiers are controller routing metadata only.  Model
requests contain each row's caller-provided `review_material`, never a case
identifier or an expected state.

For each neutral, positive, and negative pressure variant the compiler projects
the same bundle and budget into the scenario.  The driver changes only the
pressure instruction.  It makes four review requests plus one final bounded
decision request, all recorded in the `RunSession` journal with an opaque panel
cell digest.

Each row carries caller-supplied `admission_checks`: a validator identity and
verification bit, execution result, required audit list and `AuditItem` rows,
subject bindings, and evidence IDs.  M1-on calls `EvidenceAdmission.decide`
after the matching review response provides its candidate validity, support,
novelty, investment, and polarity judgement.  The driver neither supplies an
`admitted` bit nor writes an `EvidenceLedger` record; evidence-ledger mutation
is M2 bookkeeping.  M1-off retains the same candidate judgements in the trace
with no gate intervention.  These in-process caller checks do not establish an
independent scientific authority.

The driver is registered in the production panel runner. Actual admission
decisions (or explicit M1-off dispositions) reach the final request as well as
the journal; final decisions can therefore use the gate result. Untyped planning
fixtures remain non-executable at this driver and cannot stand in for real
caller-supplied evidence.

Each initial review request uses only its selected caller-provided public
material.  Its top-level context has an empty evidence ledger, so no other-case
material or private check fields reach the model.  The final request in both
M5 arms receives the complete public material and all actual candidate/review
responses.  M5-on represents reviews as sealed submissions; M5-off represents
the same responses as raw unverified control material.

M5 opens a sealed `ReviewEngine` session, stores four submissions, and reveals
only after all submissions.  Its disabled arm makes the same four model calls
with an explicit control record and no review submission.

The driver records engineering provenance only.  It neither scores FP/FN or
pressure flips nor provides a validation or acceptance path.  An independently
configured scorer and validation lease remain required for those claims.
