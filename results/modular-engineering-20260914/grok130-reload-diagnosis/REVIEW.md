## Proven call-chain behavior

1. `agent_config_full.rs:752–781`: AgentDefinition uses camelCase deserialization and exposes `discoverSkills`. `mvp_agent_ops.rs:3871–3935` describes and implements profile resolution, including ACP `_meta.agentProfile` and CLI profile. A strict model harness may precede the profile; this review does not recommend overriding that policy.
2. `agent_builder.rs:682–696`: absent an explicit preloaded-skills list, `discover_skills=false` produces an empty startup list. A preloaded list precedes this branch, so the flag alone is not a universal prohibition on every source.
3. `agent_builder.rs:1174–1190`: the same flag only changes discovery cwd to `None`; the builder still calls `seed_skill_discovery` unconditionally. `tools_bridge.rs:302` uses `get_or_default::<SkillManager>()`. Therefore an empty SkillManager is still created. `skill_tracker.rs:328–365` seeds empty startup state without a pending reminder when no skills exist.
4. `session_setup.rs:200–228`: reload reads the current SkillsConfig and plugin registry, re-runs disk/plugin discovery for session cwd, then updates the baseline and applies pending effects. There is no `discover_skills` test in this function.
5. `skill_tracker.rs:375–387`: replacing the empty baseline with different paths queues a BaselineChange. `skill_tracker.rs:436–484` combines runtime skills and renders a system reminder. `tools_bridge.rs:405–414` writes the runtime projection into AvailableSkills. `session_setup.rs:335–356` advertises commands and either appends the reminder to conversation or queues it for a running turn. Therefore reload can change actual model context even if tool definitions remain empty. The cursor harness has a separate reminder suppression rule; that is not a proposed workaround for the ordinary profile.
6. `app.rs:193–239`: a filesystem watcher injects an internal request with ID `skills-reload`. `session_admin.rs:633–637` returns `{reloaded: ...}`. `mvp_agent_ops.rs:60–68` shows this value is the count of resident session IDs after enqueuing ReloadSkills, **not skill count, acknowledgement of completion, or proof of an empty context**.
7. `mvp_mod.rs:2160–2165,2298–2347`: successful background bundle synchronization also broadcasts RefreshSkillBaseline directly. A recognized `skills-reload` wire response is therefore not a complete inventory of potential skill-context refreshes.

## Official configuration isolation and its limits

`prompt_skills.rs:22–46` defines `[skills] paths`, `ignore`, `disabled`, `server_skill_dirs`, and `bundled_skill_dirs`. `ignore` is an exact canonical path-prefix filter (`624–643`), not a glob. An absolute isolated bundle-root prefix can exclude subsequently downloaded ordinary bundled skills without blocking downloads or altering platform behavior. Empty `bundled_skill_dirs` does not suppress automatic discovery of `<GROK_HOME>/bundled` (`322–329`). The isolated home/cwd and no external config paths must remain bound to the deployment envelope.

Crucially, `prompt_skills.rs:112` filters ordinary skills **before** plugin skills are collected and merged at `115–121`. Thus `ignore` does not cover plugin-provided skills in this implementation, despite the broader comment at line 57. `disabled` is an explicit skill-name list, not a blanket switch, and leaves disabled skills in the list. `agent_config.rs:893–907` offers plugin paths, explicit disabled IDs/names, and enabled IDs/names; no global plugin-off switch was found in that type. Empty `plugins.paths` alone does not prove no automatically discovered plugin sources. For this bounded isolated readiness route, retain an empty controlled home/cwd and no plugin sources, or freeze explicit official disabled IDs for every known plugin. Do not claim `ignore=["*"]` or `paths=[]` disables all skills/plugins.

The watcher starts from discovery roots without consulting `ignore` (`config_watcher.rs:676–695`), so an ignored bundle can still cause a `skills-reload` response. Configuration isolation and wire-response classification are distinct requirements.
